## MAJOR-1 (T-635) — the HUD's "own slot" is inside the right dock's footprint and z-order; there is no reachable state where the relocated HUD is legible

**Evidence.** The HUD mounts on the full-bleed chrome overlay (`absolute inset-0 z-10`, mission_editor.rs:2218) as `absolute right-3 bottom-3`, **no z-index** (:2296). Its sibling DockRight wrapper is `absolute bottom-0 right-0 top-12 z-20 w-80` (:2257) and `DOCK_R` is a full-height, painted panel: `bg-surface-container-lowest/55 … backdrop-blur-xl h-full overflow-y-auto` (eden_layout.rs:41). The HUD rectangle (right edge 12 px from viewport, text ~260–320 px of 11-px mono, bottom band 12–27 px) sits entirely inside the dock's 320-px column, which reaches `bottom-0`. Positioned siblings: `z-20` paints over `z-index:auto` regardless of DOM order, and `backdrop-blur-xl` additionally blurs everything painted behind the panel. So with chrome visible the HUD renders **behind the asset browser** — tinted and blurred into illegibility; with chrome hidden the HUD's own gate `!chrome_hidden.get() && …` (:2293) **unmounts it**. Toggle on, toggle off: nothing an operator can see. The 4 new t635 tests are source-inspection (DOM nesting + gate expression + class strings) and structurally cannot see stacking or geometry — they all pass over this.

**Impact.** The ticket's deliverable — a visible telemetry HUD that no longer collides with readouts — ships as an invisible HUD. The overlap with the toolbelt is gone only in the sense that nothing renders. Also falsifies the shipped comment/commit "overlap geometrically impossible" (:2285): that property is DOM-nesting-only; even against the toolbelt pill, two absolutely-positioned siblings can overlap at narrow widths (derivation: pill ~580 px per T-636's own measurement → half-width 290; HUD ~300 px + 12 px inset; `290 + 312 > w/2` ⟹ boxes intersect below w ≈ 1200 px) — moot today only because the dock buries the HUD first. Note the old pre-T-635 position, for all its readout-painting sin, was at least visible.

**Disposition.** Reposition required before the HUD is real: inset left of the dock column (`right-[calc(20rem+0.75rem)]`), or anchor to the map pane instead of the viewport, or `z-30` + accept riding over the dock's bottom padding. Interacts with T-636 (full-width status bar will claim the bottom band; its registry summary names CUR/OBJ/SEL/SZ and a right-end action slot — it contains **no rf-HUD mention**, contrary to the claim sheet, so nothing forward-plans this slot either). Documented only; nothing fixed.

## MAJOR-2 (T-666) — an aborted layer drag leaves a live latch; the next "+" click silently reparents the stale folder to root

**Evidence.** `PENDING_LAYER_DRAG` is armed on **every** folder/slot row `pointerdown` (editor_ops.rs:1316/:1322 via eden_tree.rs:676-683/:747-762) and cleared only by: in-dock completions (folder-row pointerup :684-694, header dropzone eden_dock_left.rs:55-63), the tree wrapper's stray-catcher pointerup (eden_dock_left.rs:90-95), or overwrite by the next row pointerdown. A drag released **outside the dock** (over the map / right dock / strip — the ordinary overshoot abort) leaves the latch armed indefinitely: Esc has no handler (only the rename input consumes Escape), Backspace hide-chrome unmounts the dock with the latch still set, and no window-level pointerup exists. The armed `Folder` latch then completes on any header pointerup that lacks a prior row pointerdown — concretely the **"+" button**: it is inside the header dropzone div; its `on:click` stops click propagation but nothing stops its **pointerup** bubbling to the header's `on:pointerup` → `complete_layer_drop_onto_root()` (:59) consumes the stale latch and reparents the long-forgotten folder to root, then the click creates the new layer. Two mutations, one visible. (A stale `Slot` latch is safer: the root dropzone drops it (:1353-1358), and the map's pointer capture (mission_editor.rs:1541/:1671) forecloses most map-originated releases onto folder rows.) The "mirrors ORBAT" claim is honest about the idiom but not the containment: ORBAT's latch lives inside a modal whose dialog-level `on:pointerup` cancels every non-target release (orbat_manager.rs:339-343); the dock mirror has no equivalent outer catcher. Plain folder clicks are clean — self-arm then self-drop no-ops (`id == dest` → false, latch consumed, :1340-1342).

**Impact.** Silent structural doc mutation (undoable, but unannounced and off-screen if the tree is scrolled) triggered by a routine affordance after a routine aborted drag. Also the B-question answer: mid-drag Backspace/Esc is **neither cancelled nor wedged** — the latch invisibly persists (there is no drag ghost/affordance at all to wedge).

**Disposition.** Clear the latch on any non-completing release: a window-level pointerup fallback, or cancel on dock `pointerleave`, or stop pointerup propagation on the "+" button. Same fix should add an Esc cancel. Document-only here.

## MAJOR-3 (T-666 × T-715, cross-slice) — hidden-layer slots enter the selection by design, and every downstream consumer then acts on them sight-unseen

**Evidence.** Deliberate and tested: folder-click selectors read the unfiltered doc (`layer_rows` → `entityIds`), rationale comment at eden_tree.rs:16-33, pin tests `selection_reads_unfiltered_doc_hidden_layer_still_selects` + `selection_uses_layer_rows_not_materialize`; the store.rs:465-473 citation in that comment is accurate at HEAD (:467-473 hidden-layer `continue`). What the comment does **not** cover is every consumer of `ctx.selection`:

- **Delete** — `delete_selection` (editor_ops.rs:339) reads the selection verbatim → `remove_slots` deletes invisible slots, no confirm, map showed nothing tinted.
- **Drag-move** — `compute_move_ids` (select_tool.rs:189) folds hidden ids in when a visible member is dragged; `move_entities_and_vehicles` (mission_editor.rs:1914) moves them at doc level; the drag preview cannot show them (`pack_drag_overlay` skips ids absent from the SoA — the materialized SoA does **not** carry hidden slots). They teleport with zero preview.
- **SEL count** — `refresh_selection` sets `sel_count = selection.len()` (mission_history.rs:341-349): the toolbelt counts invisible slots while the map tints fewer; with exactly one hidden slot selected, the toolbelt XYZ silently falls back to CUR (`read_attrs` materializes → `None`, editor_ops.rs:643-650, eden_toolbelt.rs:53-63).
- **Ephemerality** — `after_doc_change` prunes the selection against the **filtered** `soa.ids` (mission_history.rs:369-373): any next doc edit anywhere (rename a layer, move another slot, place a unit) silently evicts the hidden ids. So the hidden-selection is real for exactly the destructive reads (Delete, move, copy) and evaporates on everything else.

**Impact.** This is a new incoherence lane **on top of** T-715, not just adjacent to it: T-715 is "hidden slots vanish from the docks"; this adds "…but they can be selected, counted, moved and deleted while invisible, and the selection self-erases on the next edit". When T-715 is fixed (rows return, dimmed), the selection will *look* coherent while these behaviors persist unstated — the exact wave-105+ trap the wave brief predicted.

**Disposition.** Product decision, not a code bug per se: either prune hidden ids at selection time (contradicts the ticket's own spec) or teach the consumers (confirm on Delete when the selection includes hidden slots; SEL as `visible/total`; exempt hidden ids from the drag fold). Must be resolved by whichever wave takes T-715. Document-only.
