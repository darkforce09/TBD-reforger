## MAJOR-1 (T-647) — PLACE-001 "click-then-click" does not exist end-to-end: the dock click cancels itself, and the picker click places instantly at the picker row's position

**Evidence.** (a) Dock path: a palette leaf arms on `pointerdown` (eden_dock_right.rs:161-173, unchanged this wave — T-647 touched only editor_ops/mission_editor). The chrome host stops `pointerdown` only ("a release over a dock ALSO bubbles here" — mission_editor.rs:1944-1946), so the arming click's own `pointerup` over the dock reaches the place branch, fails the on-canvas inset check (:1953-1956) and hits `None => cancel_pending()` (:2002). A plain click on a leaf is arm-then-cancel — the "next canvas click" finds nothing armed. This is the T-159.22 drag-to-place design (editor_ops.rs:1466 "dropped by cancel_pending on a release over chrome") and T-647 shipped no code to change it; its PLACE-001 delivery is the comment + gate pin only. (b) Picker path: an `AssetPickerOverlay` row arms on `pointerdown` (stop_propagation, `begin_place`, `close_asset_picker` — mission_editor.rs:766-786). The release of that same click lands ~100 ms later over the canvas (the picker floats mid-canvas and its DOM is gone — and even unremoved, only pointerDOWN is stopped; the whole overlay is a descendant of the gesture container, node_ref :2454, mount :2605), so the armed place branch fires: `has_pending()` true → on-canvas → `place_at_alt` at the **release** px. The asset places immediately, at the picker row's screen position (up to a panel-height away from the dblclicked point), not on a deliberate second click. `AssetPickerState.wx/wy` is never read by any placement (annotated as such). If the row happens to lie inside a dock inset band, the same release instead **cancels** — the pick is silently dropped.

**Impact.** The slice's headline id is not delivered: no surface in the editor supports click-then-click. The picker — the one new entry point — behaves as "click lands it here, now", at a point the operator did not aim at; the claim "the operator's next canvas click lands it (PLACE-001)" (repeated in five comments and two test names) is false. The 9 pins cannot see this: they pin `begin_place` + `has_pending()` wiring as source text, and the defect is event-sequencing.

**Disposition.** Document only. Fix shape for the owning wave: arm on `click` (fires after pointerup) for both the leaf and picker rows, or add a consume-one-pointerup latch when arming from a pointerdown surface; and require `ev.button() == 0` in the place branch (see MAJOR-3). Re-word the PLACE-001 comments/pins to whatever contract actually ships.

## MAJOR-2 (T-647) — armed canvas clicks leave a stale `LG::Pending`; after disarm it promotes into a phantom button-less drag whose commit can teleport the just-placed entity

**Evidence.** A canvas `pointerdown` while armed still writes `left = Some(LG::Pending)` (:1695-1719 — no `has_pending` check); `pointermove` while armed returns before the gesture machine (:1778-1785); the armed `pointerup` place branch returns without taking `left` (:1947-2010). Net: every click of a Ctrl multi-place run (PLACE-004 — the one armed-canvas-click chain reachable today) strands a `Pending` at the click point. When the arm ends (final no-Ctrl stamp), the very next bare `pointermove` runs the gesture machine on the stale `Pending`: ≥4 px of travel (`DRAG_THRESHOLD_PX = 4.0`, select_tool.rs:31) promotes it — the pick at the press point hits the entity just placed there → `LG::Move { ids: [placed] }`, selection silently replaced (:1830-1855), drag preview glued to a button-less mouse. The phantom `Move` then **commits** on the next `pointerup` of any button — the pointerup handler never filters buttons — e.g. an RMB context-menu click or an MMB pan end: one real `move_entities_and_vehicles` txn with whatever dx/dy the bare mouse accumulated. If the stale pick misses, the promotion is a phantom **marquee** instead. The T-159.22 invariant comment that used to make this impossible ("`left`/`pan_px` are both None here", :1940-1946) is now false — T-647 broke it and left it standing.

**Impact.** Repro from a mundane flow: drag a unit out with Ctrl held (stamp 1), click twice more (stamps 2-3, last without Ctrl), wiggle the mouse, right-click → the last-placed entity teleports to the wander point (undoable, one txn) and the context menu opens over the wreckage. Lesser symptom on the overwrite path: clicking instead of right-clicking abandons the phantom Move with the preview offset still applied — the placed glyph renders displaced from its doc position until the next rebind. Answers priority-A directly: a drag can never reach the regroup arm **while** armed (pointermove's armed return prevents promotion — the claim's mutual exclusion holds), but the armed state leaks a gesture that outlives the arm.

**Disposition.** Document only. Fix shape: the armed place branch must also `left.borrow_mut().take()` (and the promotion path should require `ev.buttons() != 0`).

## MAJOR-3 (T-647) — the armed place branch consumes every button: MMB "pan while stamping" places the entity, kills the pan, and latches a phantom pan; RMB places instead of cancelling

**Evidence.** While armed: MMB `pointerdown` still opens a pan (`pan_px` set, capture, `set_camera_gesture(true)` — :1687-1694), but `pointermove` returns at the armed gate before the pan branch (:1778-1786) — the camera never moves; MMB `pointerup` then enters the place branch first (:1947, no button check), **places** at the release point and returns before the pan-end cleanup (:2013-2025), leaving `pan_px` latched and the camera-gesture flag stuck true (heavy zoom-band recompute suppressed). After the arm ends, the first bare `pointermove` finds `pan_px` Some → the camera jumps by (now − stale anchor) and pans with the button-less mouse until the next pointerup clears it. RMB while armed: `pointerdown` does nothing (RMB no longer pans, T-662), `pointerup` → place branch → places; the `contextmenu` event then opens the menu over the fresh entity — Eden's stamp-mode RMB-cancel idiom stamps instead. And there is **no keyboard disarm at all**: Escape is bound to the picker, dialogs and menu but never to `cancel_pending` (grep: cancel_pending is called only from the off-canvas release :2002 and `pointercancel` :2283) — mid multi-place, the only exits are a no-Ctrl click (places one more) or deliberately releasing over chrome.

**Impact.** Mid-run camera adjustment — a natural need while stamping a line of vehicles across the map — misplaces an entity and then throws the camera; the two Eden-native cancel gestures (RMB, Esc) respectively misplace an entity and do nothing. Together with MAJOR-2 this makes PLACE-004 hostile in exactly the flows Eden users will try first.

**Disposition.** Document only. Fix shape: place branch gated on `ev.button() == 0`; run the pan-end cleanup before/inside the armed branch for button 1; bind Escape → `cancel_pending()` (+ ghost clear) in the editor keydown.

## MINOR-2 (T-691) — stacked dialogs, one Esc closes both: Editor Preferences copies the hand-rolled window-Esc idiom instead of the modal stack

## NOTE-1 (T-691) — migration precedence and residue: the new store always wins, and the legacy keys are never deleted

Once `tbd-mc-editor-prefs` exists, the legacy keys are never read again (world_layer_prefs.rs `load_store`: versioned key short-circuits) — a user who runs a pre-T-691 build after the migration (old build writes legacy keys) silently loses those later changes on returning to the new build. Defensible for a one-way, no-timestamp migration and documented as "read at most once", but it is last-write-LOSES for the old build, and the stale legacy keys linger in localStorage indefinitely (migration never re-fires, so they are inert residue, not a correctness risk — unless the operator deletes only the new key, which resurrects the frozen legacy state). Quota/private-browsing verified safe: `storage()` collapses every failure to None (defaults, save no-op), `set_item` errors are discarded — no panic path. Double-mount: `MissionSettingsDialog` mounts exactly once (mission_editor.rs:2573); the `thread_local` open-signal is last-writer-wins, currently safe, and would silently rebind the opener if a second mount ever appeared.
