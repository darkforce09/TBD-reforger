## MAJOR-1 (T-650) — the composition row's advertised "Click to arm, then click the map to place" is the exact flow wave-106 MAJOR-1 proved self-cancelling; the headline place gesture works only as an unadvertised drag

**Evidence.** The Composition leaf title is the odd one out: `leaf_title()` returns "Drag onto the map to place" for Character/Vehicle/Object but **"Click to arm, then click the map to place this composition"** for Composition (eden_dock_right.rs:78-83), repeated on the row itself (`title="Click to arm, then click the map to place"`, :1157). The row arms on `on:pointerdown` (:1159 → `begin_place_composition`), the same idiom as palette leaves. The chrome host stops **pointerdown only** (mission_editor.rs:2736-2739 `on:pointerdown=|ev| ev.stop_propagation()`; the T-159.22 comment at :2154-2156 says so in words), so the arming click's **own pointerup** bubbles into the container's armed-place branch (:2157), fails the on-canvas inset check (px inside the right-dock 320-px band, :2168-2171), and hits `None => cancel_pending()` (:2217). Arm-then-cancel inside one click, ~100 ms. This is byte-for-byte the mechanism wave-106 recorded as **MAJOR-1 ("PLACE-001 click-then-click does not exist end-to-end: the dock click cancels itself")**, with the fix shape written down ("arm on `click`… or a consume-one-pointerup latch"). The palette_rows doc comment even acknowledges it: "the release is consumed by the container's `pointerup`" (eden_dock_right.rs:90-91). T-650 shipped no code against that machine — it shipped new affordance text promising the broken half.

**Impact.** COMP-PLACE-001's user-facing contract never fires: an operator following the tooltip clicks the row (arm+cancel, silent) then clicks the map (plain select click — nothing places). The feature IS reachable — press-drag from the row onto the canvas places correctly (verified path: `has_pending` → on-canvas → `place_at` → `Pending::Composition` arm → `place_composition` one-txn), and a Ctrl-kept arm stamps on subsequent canvas clicks — but drag is exactly what the Composition tooltip, uniquely among the four kinds, does not say. The `delete_composition` code carefully clears an arm "so a release cannot commit a composition that no longer exists" — an arm that in the click flow never survives its own release.

**Disposition.** Document only. The owning wave should implement wave-106's prescribed fix (arm on `click`, or a consume-one-pointerup latch) for leaf + picker + composition rows together — it is one root — or reword the Composition tooltip to the drag contract that actually ships. Until then the tooltip is the corpus's dead-control lie in text form: T-642's module header cites "two dead-control cautionary tales" as THE RULE while its sibling slice shipped a third.

## MAJOR-2 (T-642) — the ruler's Escape arm double-fires with every open overlay: dismissing the context menu also deletes the placed measurement

**Evidence.** The ruler Esc arm is an unguarded window-keydown match arm: `"Escape" if !modk => { ruler.borrow_mut().escape() … }` (mission_editor.rs:1309-1314) — no check that a menu/dialog/picker is open, and no registration with the T-333 `modal_stack` ("one Escape, one dialog", ui.rs:98-137, built after T-226 lost user edits to exactly this class). The context menu owns its own window-level Esc closer (context_menu.rs:512), as do the asset picker (mission_editor.rs:729), Attributes (attributes.rs:36), Settings (eden_settings.rs:87), ORBAT/Faction managers. Separate window listeners all fire on one keypress; `prevent_default` does not gate siblings. The collision is reachable in the only mode a chain can exist: RMB opens the context menu regardless of tool mode (oncontextmenu is unconditional, :2462-2501).

**Impact.** Deterministic repro: Ruler tool → click points → dbl-click (ends chain, keeps it placed) → right-click anything (Eden's inspect gesture) → **Esc to close the menu → the menu closes AND `escape()` runs on the non-drawing chain → `points.clear()` — the whole placed measurement is gone** (ruler_tool.rs:331-345, the not-drawing arm). Mid-draw the same press costs the drawing state (lesser: the next click re-arms onto the same points). The two-step Esc escalation was designed precisely to protect a placed measure from an accidental Esc; an open overlay defeats it on the first press. This is the third instance of the class the repo has a named contract for.

**Disposition.** Document only. Fix shape: guard the arm on "no overlay open" (context menu signal + picker + `modal_stack` top), or register the ruler as an Esc consumer in `modal_stack` with the map as the bottom of the stack. One-line-ish in the owning wave; pair it with a pin that Esc-with-menu-open leaves the chain intact.

## MINOR-2 (T-650) — the save affordance can't see selection changes: it subscribes to `doc_tick`, but selection updates never bump it, so the canonical save flow shows the empty-state against a live selection

**Evidence.** The compositions panel's gate closure reads exactly one signal: `let _ = doc_tick.get(); if ops::selection_len() == 0 { …empty-state… }` (eden_dock_right.rs:888-897); `selection_len()` reads a `RefCell`, not a signal (editor_ops.rs:389-395). A map click/marquee runs the selection-only tail — `sel_count` + `selected_ids` set, explicitly **no doc-side tick** (mission_history.rs:341-350; mission_editor.rs:2280-2282 "a click changes the selection, not the document"). So the canonical flow — place/arrange entities (doc edits), then marquee-select them (no doc edit), open Compositions — renders "Select one or more placed entities to save a composition." against a visibly live selection until the next unrelated doc edit. The inverse staleness offers "Save composition… (N selected)" after a deselect; pressing Save then hits `save_composition`'s empty-selection `None` and the form closes as if it saved (dock diff: `save_open.set(false)`, fields cleared, no feedback).

**Impact.** COMP-SAVE-001's primary path dead-ends behind a non-obvious workaround (make any doc edit); the failure mode is a silent no-op save. The five source pins can't see it — it is reactivity wiring, not source shape.

**Disposition.** One-line fix in the owning wave: subscribe the closure to `ctx.selected_ids` (already an `RwSignal`, already pushed on every selection change via `refresh_selection_mirrors`) instead of / beside `doc_tick`; add a "Save with empty selection reports, not swallows" behavior.

## MINOR-4 (T-658) — `EvalContext`'s documented construction idiom is a compile error in the crate the doc names: `..Default::default()` cannot construct a `#[non_exhaustive]` struct cross-crate

**Evidence.** validate.rs:71-74: "`#[non_exhaustive]` on purpose… callers build the context with `..Default::default()` so they never have to name every field"; :88-89 repeats the form for "the SPA panel (T-655 W111)". RFC 2008 / E0639: outside the defining crate a non-exhaustive struct cannot be built with ANY struct expression — functional-update syntax included. The SPA (`website-frontend`) is another crate; the documented pattern will not compile there, ever. What DOES work cross-crate: `EvalContext::with_known_asset_ids(ids)` (:91, exists, covers today's single field) and `let mut c = EvalContext::default(); c.known_asset_ids = …` (pub field mutation is allowed). The moment T-660 adds a second field there is no documented cross-crate way to combine fields.

**Impact.** T-655's wiring wave hits E0639 following the in-file instructions; same-crate tests are structurally incapable of catching it. Contained (the constructor escape hatch exists), but the doc is authoritative-sounding and wrong.

**Disposition.** Doc fix in the owning wave (name the constructor + default-then-mutate as the cross-crate forms); consider a builder or `set_*` methods when T-660 lands its fields.
