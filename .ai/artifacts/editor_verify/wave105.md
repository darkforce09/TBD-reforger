## BLOCKER-1 (T-646) — the `class:` recogniser byte-slices at a non-char boundary: typing "beauté" into any asset search panics the wasm app

**Evidence.** `strip_prefix_ci` (asset_catalog.rs:449-455): `s[..prefix.len()]` with `prefix.len()==6` — a raw byte slice. Rust `str` slicing panics when byte 6 is not a char boundary, i.e. any query ≥6 bytes whose 6th byte falls inside a multibyte char. Confirmed empirically on the extracted function (scratchpad, rustc): `"beauté"`, `"abcdeß"`, `"a日本"` all panic (`end byte index 6 is not a char boundary`); `"café"`, `"señor"`, `"straße"` survive only by byte-length luck. Reachability: all three dock search inputs feed the raw `on:input` string into `filter_catalog(&nodes, &q)` **and** `search_empty_message(&q, …)` (eden_dock_right.rs:587/:645/:744), both of which call `parse_search_query` → `strip_prefix_ci` on every keystroke. In wasm a panic aborts the Leptos runtime — the whole Mission Creator dies mid-keystroke (reload required). Every shipped test operand is ASCII, so the 17-test module never touches the boundary.

**Impact.** A hard editor crash from ordinary typed input in the feature's own entry surface (assets, objects, vehicles search). "beauté", "Straßé", any 5-ASCII-then-accent shape, any `a+CJK` shape. This is the panic class the codebase's own `eq_ignore_ascii_case` comment thinks it is avoiding ("avoids allocating") — the allocation was traded for a boundary panic.

**Disposition.** Document-only per rules. One-line fix shape for the owning wave: guard with `s.is_char_boundary(prefix.len())` in the condition (or compare via `s.get(..prefix.len())`). Add a non-ASCII needle to `parse_search_query_recognises_class_operator` so the boundary stays covered.
