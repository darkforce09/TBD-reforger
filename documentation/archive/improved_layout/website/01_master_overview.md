# Subsystem master overview

**Status:** Proposed design  
**Scope:** `apps/website` and deployment infrastructure  
**Context:** TBD Reforger platform monorepo  

The master architectural overview and combined synthesis of the reorganization plan for the
`apps/website` subsystem.

---

## 1. Executive Summary

The `apps/website` subsystem powers the TBD community's web platform, including player
authentication, event slotting, ORBAT coordination, server telemetry, the Mission Creator, and
headless spatial computation. Over successive development milestones, the core functionality of
`api_v2`, `frontend`, `map-engine`, and `graphics-engine` has matured significantly. However,
directory layout and configuration artifacts have accumulated several structural inconsistencies:

1. **Scattered container and deployment configs**: Compose files for local development and staging
   were split across `apps/website/api_v2/` and `apps/website/`, with the production `Dockerfile`
   sitting at the website root.
2. **Ambiguous frontend naming**: The client-side HTTP/SSE transport layer inside `frontend` was
   named `core/api`, creating severe ambiguity with the backend Axum crate `api_v2` (`website-api`).
   The frontend is a consumer of the API, not an API host.
3. **Duplicate wire DTO types and parity fixtures**: The frontend hand-duplicated wire DTOs and
   maintained 15+ test files in `dto/tests/` to track contracts already generated by `typify` in
   `api_v2`, because the frontend could not import the heavy server crate `website-api`.
4. **Inverted dependency leaks (`core` ➔ `apps`)**: Foundational UI components in `core/ui/` imported
   styling tokens from `apps::editor`, while `core/auth/store.rs` hardcoded an IndexedDB document
   purge call into the Mission Creator editor application.
5. **Misplaced application shell**: The root `AppLayout`, `TopNav`, and `Sidebar` chrome components
   were nested under `pages/navigation/` rather than a dedicated application shell layer.
6. **Backend test compilation bloat**: 95 integration test files were dumped flatly in
   `apps/website/api_v2/tests/`, causing Cargo to compile 95 separate test binaries on every run.
7. **Ad-hoc root directory**: A single-file directory `apps/website/shared/` existed at the root
   solely to house an 86-item URL scheme guard test table.
8. **Orphaned frontend directory cruft**: An empty, untracked `src/v2/map_engine/` folder remained
   in `frontend` from an earlier phase before engines became top-level peers.

This reorganization resolves these issues systematically, ensuring the codebase is predictable,
strictly modular, easily maintainable, and compliant with all monorepo verification gates.

## 4. Key Architectural Principles

1. **One API Location**: All API route handlers, database schemas, background workers, and shared
   wire data types reside under `apps/website/api_v2/`. When touching the API, there is only one
   place to go.
2. **Strict One-Way Dependency Flow**:
   $$\text{apps (CAD workspaces)} \longrightarrow \text{pages (routed docs)} \longrightarrow \text{shell (chrome)} \longrightarrow \text{core (foundations)}$$
   No foundation module (`core`) may import from `pages` or `apps`. Design tokens live in `core/ui/tokens.rs`,
   and application cleanups register via event hooks in `core/auth/`.
3. **Frontend Has a Transport Layer, Not an API**: The frontend is an API consumer. Its network
   module is named `core/transport/`, reflecting its true responsibility: browser HTTP fetch,
   SSE telemetry streams, tab concurrency locks, and token refresh single-flight.
4. **No Duplicate DTOs**: By creating `website-api-types` as a lightweight crate without Tokio/SQLx,
   both the backend and the WASM frontend link the exact same Rust structs, completely eliminating
   duplicated types and 15+ fixture parity test files.
5. **No Single-File Root Directories**: `is_http_url_cases.rs` is absorbed into `api_v2/types/`,
   leaving the website root clean, comprising only Cargo crates and dedicated peer folders.
6. **Option B Documentation Strategy**: To prevent CI failures against the monorepo's
   `markdown-placement` gate (Rule 1: code trees hold only `README.md`), all multi-file
   specifications live in `documentation_v2/website/improved_layout/`, while
   `apps/website/improved_layout/README.md` acts as a code-tree anchor.
