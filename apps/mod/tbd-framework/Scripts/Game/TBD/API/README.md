# API

REST communication layer interfacing the game server with the `website-api` platform.

### Roles & Responsibilities
- `TBD_BackendConfig.c`: Server configuration loader reading the backend URL and both credentials (`serverToken`, `machineCredential`) from `$profile:TBD_BackendConfig.json`. `Reload()` re-reads the file while the server runs and keeps the settings in force when the file does not read or parse. The mission and its event are not configured: the server runs the mission deployed to it on the platform (`Systems/Mission/Loaders/TBD_DeployedMission.c`).
- `TBD_PlayerIdentity.c`: Canonical accessor for the player engine GUID (`arma_id`), guaranteeing byte-for-byte consistency across all backend endpoints.
- `TBD_IdentityLink.c`: Handles in-game `#tbd link <code>` chat commands and issues confirmation requests to the platform.
- `TBD_ResultsReporter.c`: End-of-round match telemetry reporter compiling player attendance, roles, and match outcomes.
- `TBD_GameRuntimeHttp.c`: Shared transport of the `/api/v1/game-runtime/` and `/api/v1/fleet-executor/` routes. `Post` / `Get` open a context carrying the machine credential as a bearer and deliver exactly one answer to the sender's `TBD_GameRuntimeCall` subclass, including a TRANSIENT answer from a watchdog when the engine never reports a request. Also the backoff arithmetic and JSON string escaping.
- `TBD_GameRuntimeAnswer.c`: One answer read from the engine's callback, classified as success, 409 fence refusal (with its parsed `details`), transient or permanent; the `details.code` of any error status (`NO_DEPLOYMENT`, `ARTIFACT_NOT_DEPLOYED_HERE`, `IDENTITY_NOT_LINKED`, ...) is kept for the caller.
- `TBD_RuntimeSession.c`: The runtime session of this server: started once the world has decided what it runs, reporting the loaded mission artifact (`{loaded_artifact_id, loaded_artifact_sha256}`, or `{}` for none) - the report that confirms a mission deployment; kept alive by heartbeats with a strictly increasing sequence, restarted when it expires, stopped with an ERROR when another runtime supersedes it or the credential is revoked. A report the platform rejects (422 `UNKNOWN_ARTIFACT`, 400) is an ERROR and the session starts without one. Without a usable machine credential it holds no session and looks for one every minute. `GetSessionId()` is the session other systems address.
- `TBD_RuntimeSessionWire.c`: The session start answer and the call that carries a start or heartbeat.
- `TBD_LoadedArtifactReport.c`: What this world's session start reports: the loaded artifact (id and SHA-256 of the exact bytes) or none. Decided once per world by `TBD_DeployedMission`, cleared when the world ends.
- `TBD_RuntimeSessionClosing.c`: Closes the session of a world that ended: an offline heartbeat, then the end route. The next world's session starts only after it.
- `TBD_RuntimeSessionLifecycle.c`: `modded SCR_BaseGameMode` - starts the runtime session and the fleet command claims when the game starts on the authority of a framework world and stops both when the world ends.
- `TBD_RuntimeStatusReadings.c`: The live readings a heartbeat carries: player count, player limit, server FPS, uptime, in-game time and weather.
- `FleetCommands/`: the game runtime as a fleet command executor.
  - `TBD_FleetCommandPoller.c`: while the world holds a runtime session, claims the next command every 5 s (`POST /api/v1/fleet-executor/commands/claim` with `{runtime_session_id}`), one command at a time; 204 means nothing is claimable; a claim refused because the session ended goes to `TBD_RuntimeSession`.
  - `TBD_FleetCommandExecution.c`: the protocol of one claimed command: arguments checked again, `executing` reported and admitted BEFORE any effect, the effect run once, the outcome reported (`succeeded` with `outcome`, or `failed` with a reason). Reports without an answer are sent again with backoff (2 s to 30 s); any 409 abandons the command with no further effect or report, except a result report refused because the command already stands `succeeded` (an earlier attempt of that very report was recorded).
  - `TBD_FleetCommandArguments.c`: the exact argument checks (only the action's own keys, bounded text without control characters, UUIDs, 64-hex digests) and the preconditions: the command's `runtime_session_id` must be this runtime's session, a kicked player must be connected. Any other action is "not a game-runtime action".
  - `TBD_FleetPlayerActions.c`: `broadcast` (chat to every connected player, outcome `{delivered_to}`) and `kick` (the reason told in chat, the kick 2 s later, outcome `{kicked_player_id, arma_id}`).
  - `TBD_FleetLoadMissionAction.c`: `load_mission`: the deployment in effect must be the command's; the artifact is fetched and its SHA-256 verified, then written to the profile cache; `succeeded` with `{artifact_id, restart_requested: true}`; once that is recorded, the session is closed and the scenario restarts in-process. A fetch or verification failure is reported `failed` and nothing restarts.
### Call Flow & Contracts
Authority-only outbound HTTP client using Enfusion's `RestContext`, on two authentication tiers:
- `X-Service-Token` (`serverToken`, shared by every server): `POST /api/v1/ingest/link-confirm` and `POST /api/v1/ingest/match-results`.
- `Authorization: Bearer tbdm_...` (`machineCredential`, the `mod_runtime` machine credential an administrator issues for this one server): every `/api/v1/game-runtime/` route - `GET deployment` and `GET artifacts/{artifactId}` (`Systems/Mission/Loaders/`), `POST sessions`, `POST sessions/{id}/heartbeats`, `POST sessions/{id}/end`, `GET events/{eventId}/roster` (`Systems/Mission/Loaders/TBD_RosterLoader.c`), the deployment authorization routes used by `Systems/Spawning/`, `GET missions` and `POST deployments` (`Session/MissionSelector/`) - and the `/api/v1/fleet-executor/commands` routes (`FleetCommands/`). A `machineCredential` that does not start with `tbdm_` (the example's placeholder) counts as unset: no deployment is read (the last verified cached artifact runs, or none), no runtime session, no roster and no fleet commands, so on a deployment with an event every deployment into an event seat is refused until a credential is configured.

Wire contracts: `contracts_v2/definitions/game-runtime-session.schema.json`, `game-runtime-roster.schema.json`, `game-runtime-deployment.schema.json`, `mission-deployment.schema.json` (`RuntimeDeployment`, `DeployableMissionList`, `RelayedDeploymentRequest`), `fleet-command.schema.json` (`ClaimRequest`, `ClaimedFleetCommand`, `ExecutionStart`, `ExecutionResult`).
