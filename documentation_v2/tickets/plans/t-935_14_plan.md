# T-935.14 — Plan

## Context

T-935.11 shipped a checked reader for `objects/prefabs.rkyv` and no way to reach it. Its two
frontend consumers both call `WorldResidency::load_prefabs_gz`, which only understands gzipped JSON,
so the archive is dead weight until the residency can ingest it.

## Approach

1. New file beside the reader (`prefab_load.rs`, or a section of `prefab.rs`): build the residency's
   prefab row table, building lookup, fence lookup and glyph table from a `PrefabCatalog` rather
   than from a `serde_json::Value`.
2. `WorldResidency::load_prefabs(&[u8])` in `residency.rs` — call site only, sniffing gzip versus
   rkyv like `store.rs`'s road loader, delegating both arms.
3. `world_host.rs`: fetch `objects/prefabs.rkyv` when `manifest.objects.binary` names it, JSON
   otherwise, matching the roads and regions branches T-935.11 landed.

## Risks

The two lanes must agree exactly, and the failure is silent: a wrong building lookup makes the wrong
buildings occlude. The pin is a same-residency comparison on the committed everon corpus, not a
spot check, and the perturbation is a reordered or shifted lookup on the ARCHIVE side.

Note the absent-optional sentinel: T-935.11 uses NaN, while `archives.rs` documents zero. A real
zero half-extent would make the two disagree; everon has none today, so a test must construct one.

## Verification

- `cargo test -p map-engine-core --all-features prefab` — archive-versus-JSON residency parity on everon.
- `cargo xtask mk leptos-gates` — the fullmap smoke, which pins prefab-derived counts.
- `cargo xtask platform wave gate --slice T-935.14`.
