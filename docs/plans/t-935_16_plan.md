# T-935.16 — Plan

## Context
T-935.13 is titled "gz-JSON emit deleted" and its own requirements say "Do not delete gz-JSON
emitters still read". Correct at the time; nothing was filed to make the readers stop. So
`build.rs:483/:511/:520/:525` still emit gz-JSON, `world_host.rs:205/:209` still fetch
`roads.json.gz` and `forest-regions.json.gz`, and `flate2` is still in the `world` feature.
Both roads (T-935.6) and forest regions (T-935.11) already have shipped rkyv emitters — only the
readers are stale.

## Approach
1. Verify: build everon, list `objects/`; grep `world_host.rs` for the two gz fetches. Paste both.
2. Repoint the roads and forest readers at their rkyv archives; prove the loaded set is
   byte-identical to the gz path BEFORE deleting anything.
3. Delete the emitters, the manifest rows, `chunks/manifest.json`, and `dep:flate2`.
4. Re-run the gates that read these files (`schema_gates.rs`, `map_world_los.rs`) and confirm they
   go red for the right reason rather than silently vacuous on an `if exists` branch.
5. Perturbation: restore one gz fetch → the no-gz assertion goes red; restore, `touch`, green.
6. Correct T-935.13's title and summary in the same commit.

## Risks
- **Silently vacuous gates.** `schema_gates.rs` has an `if catalog.exists()` shape; deleting inputs
  can turn a gate green by making it examine nothing.
- **Collides with T-935.15** — both own `build.rs` and `world_host.rs`. They cannot share a wave.
- Deleting flate2 removes the shared gzip decode behind the gzip-vs-rkyv sniff; check no loader
  still depends on that fallback before dropping the dep.
