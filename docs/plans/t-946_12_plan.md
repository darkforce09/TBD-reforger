# T-946.12 — Plan

## Context

Wave 240 shipped one ticket at a time, so no `[[emptied]]` entry froze and the repack reissued label
240 to the next batch. `wave --close --tickets` asks for exactly that label and the collision guard
refuses, correctly — closing it would leave oracle 2 reading an open wave 240 at the marker's parent
and refusing every later gate. The wave is gated and verified; only the lock's bookkeeping is lost.

## Approach

1. `wave_lock::reserved_entry` — validate an operator-named set of shipped ids and return one
   `LockWave` at `ledger_floor + 1 + carried.len()`, appended after the derived carry.
2. `compile_reserving` / `repack_reserving` / `wave repack --reserve "<ids>"` in `main.rs`; the
   repack stays the only writer of `.ai/tickets/wave.lock`.
3. Tests in `wave_lock.rs`: a fixture that dissolves a wave id by id, one test pinning the defect,
   one pinning the repair plus survival across a plain repack, one pinning the three refusals.

## Risks

A reservation that outlived its close would hold a label forever. It cannot: the entry sits above
`wave_base`, and the post-close repack drops every entry at or below the new base. A reservation
that named a live ticket would record a target the ceremony refuses a step later, so status is
re-checked here against the tree rather than trusted from the caller.

## Verification

- `cargo test -p xtask wave_lock` — including the perturbation that makes `reserved_entry` a no-op.
- `cargo xtask wave repack --reserve "T-935.6 T-935.9 T-674.1"` then `cargo xtask ticket check`.
- `cargo xtask platform wave wave --close --tickets "T-935.6 T-935.9 T-674.1"` writes wave 240.
